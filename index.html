How I work

  • Build for change

    Good architecture makes future decisions cheaper. I keep clear module boundaries and isolate dependencies.

  • Share without compromise

    Multiplatform shouldn't mean lowest common denominator. Share logic and UI where it helps, keep platform behaviour where it matters.

  • SDKs are products

    Other engineers are the customers. API design and developer experience decide whether an SDK gets adopted.

  • Accessibility by default

    Semantics, focus order, touch targets and font scaling are planned from the start, not patched in later.

  • AI as a multiplier

    AI drafts and speeds up the boring parts. An engineer reviews and owns every line that ships.

  • Teach what you know

    From training 50+ engineers at Samsung to code reviews every day, sharing knowledge makes the whole team faster.

Dario Health · Android & iOS

Kotlin Multiplatform + Compose Multiplatform SDK

A shared SDK for Android and iOS. Kotlin Multiplatform shares the business logic, state and networking, and Compose Multiplatform shares the UI. Host apps configure it through a Kotlin DSL; a core journey engine drives the flow, an MVI state layer owns the state, and Compose renderers draw it with a shared design system.

  • Compose Multiplatform

Decision record

Why Compose Multiplatform for the SDK?

Context
Healthcare modules needed the same UI and behaviour on Android and iOS.
Decision
Use Compose Multiplatform for the UI layer, with Kotlin Multiplatform for logic, while keeping native host apps.
Trade-off
More setup complexity up front, in exchange for one codebase to maintain.

Decision record

Moving from MVVM to MVI

Context
SDK modules with many screens and states that had to match across platforms.
Decision
MVI with unidirectional data flow and a single state per screen.
Trade-off
More boilerplate, in exchange for predictable state and easier debugging.
